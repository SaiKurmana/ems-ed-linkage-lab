# Privacy and security

> Synthetic data — for demonstration only. This is a design discussion for a portfolio project, not
> legal advice. Real deployments need review by each organization's privacy and security officers.

## Why a non-identifying UUID helps

- **It says nothing about the person.** A version-4 UUID is 122 random bits. It encodes no name,
  birth date, address or date of service, unlike identifiers built from demographics.
- **Linkage without exchanging identifiers for matching.** Probabilistic linkage needs names, birth
  dates and times on both sides, in one place, to compute match scores. A carried UUID lets the
  analytic join use only the UUID; identifying fields can stay with each source.
- **Encounter-level, not person-level.** The UUID identifies one EMS encounter. It does not create a
  longitudinal person identifier across encounters, which limits what can be inferred by joining.
- **Auditable.** Every place the UUID is written (PV1-50, `Encounter.identifier`) is explicit and can be
  logged and reconciled.

Analogy: a coat-check ticket. The number on the ticket reveals nothing about the coat's owner, but
anyone holding both halves can match them exactly. The privacy question is therefore not the ticket
itself, but **who holds both halves and what else is stapled to them**.

## Residual re-identification risks

| Risk | Why it remains | Mitigation |
|---|---|---|
| Linked record is richer than either source | The join combines scene location (county), times, vitals, diagnoses and disposition | Release only aggregates; small-cell suppression; role-based access to linked microdata |
| UUID is a key into identified systems | Anyone with access to the ePCR or EHR can look up the person behind a UUID | Treat the UUID as confidential within systems; never publish it; tokenize/rehash it for analytic extracts |
| Quasi-identifiers | Rare combinations (age + county + date + mechanism) can single out people, especially in rural counties | Generalize dates/ages, suppress small cells, apply statistical disclosure control |
| Free text and timestamps | Precise times and narratives can identify events reported in the news | Exclude narratives; coarsen times in research extracts |
| Wrong-UUID write-back (Pattern B) | A false match attaches one person's EMS data to another's ED record | Conservative match rules, manual review, audit trail, correction process |

## Minimum-necessary principles applied in this design

1. **Send only what each step needs.** Pattern A/C payloads to the hospital carry the UUID and the
   demographics registration already collects — no clinical EMS data are needed to carry the identifier.
2. **Separate linkage from analysis.** The analytic dataset can carry the UUID (or a keyed hash of it)
   plus the analytic variables, without names or full birth dates.
3. **County-level geography.** The simulation stores incident location at county level only
   (NEMSIS eScene.21 Incident County).
4. **Purpose limitation.** Document the use case (injury surveillance, EMS QI) in agreements; new uses
   need new review.
5. **Retention.** Define how long linked microdata are kept and how they are destroyed.

## Security controls (checklist)

- Transport encryption for HL7 v2 (e.g., VPN/TLS) and FHIR (TLS + OAuth 2.0 client credentials with
  least-privilege scopes).
- Interface-engine and API audit logs retained per policy; alerting on spikes in failures.
- Separate test environments using **synthetic** data only (like this repository's `examples/`).
- Access reviews for anyone who can see both the UUID and identifying data.

## This repository

All data are generated by code with a fixed seed. Names come from Faker and small generic lists; county,
agency and hospital names are fictional placeholders (e.g. "County 05 (synthetic)"). No real patient
data are used, stored or required.
